# Vulnerable Notes защищённая версия

Учебное PHP-приложение после устранения основных уязвимостей из лабораторной работы № 2.

## Требования

- PHP 8.0 или новее с расширениями `pdo_mysql` и `mbstring`;
- MySQL или MariaDB;
- Apache с обработкой `.htaccess` (`AllowOverride All`).

## Запуск

1. Импортируйте `database.sql` в MySQL или MariaDB. Скрипт создаёт базу `vulnerable_notes`, таблицы и демонстрационные данные.
2. Укажите параметры подключения в переменных окружения веб-сервера: `NOTES_DB_HOST`, `NOTES_DB_NAME`, `NOTES_DB_USER`, `NOTES_DB_PASSWORD`. Для локальной учебной установки по умолчанию используются `localhost`, `vulnerable_notes`, `root` и пустой пароль.
3. Сделайте каталог `vulnerable-notes 2` корнем сайта и откройте `index.php`.

Не используйте пользователя MySQL `root` в рабочем окружении. Создайте отдельного пользователя БД с правами только на базу `vulnerable_notes` и задайте пароль вне каталога сайта.

### Docker

Для локальной проверки из каталога проекта выполните `docker compose up --build -d`. Приложение будет доступно по адресу `http://localhost:8080`, а MySQL будет инициализирован содержимым `database.sql`. Учётные данные базы для Docker Compose предназначены только для локальной разработки.

Чтобы удалить контейнеры и полностью пересоздать учебную базу, выполните `docker compose down -v`, затем снова `docker compose up --build -d`.

## Демонстрационные аккаунты

| Роль | Email | Пароль |
|---|---|---|
| Администратор | `admin@example.local` | `AdminSecure2026!` |
| Пользователь | `anna@example.local` | `AnnaSecure2026!` |
| Пользователь | `ivan@example.local` | `IvanSecure2026!` |

В SQL-файле сохранены только bcrypt-хеши этих паролей. Пароли проверяются функцией `password_verify()`.

## Реализованные меры защиты

- Подготовленные SQL-запросы с отключённой эмуляцией prepared statements.
- Серверная проверка формата, обязательности и длины данных.
- HTML-экранирование пользовательского текста через `htmlspecialchars()`.
- Проверка владельца заметки во всех операциях чтения, редактирования и удаления.
- Проверка роли для административной страницы; хеши паролей не выводятся.
- CSRF-токены для регистрации, входа, заметок и выхода; удаление выполняется только POST-запросом.
- Безопасные cookie-параметры, строгий режим сессии, регенерация ID при входе и полное завершение сессии при выходе.
- Пользователь получает нейтральные ошибки, а важные события и ошибки записываются в `storage/app.log`.
- `.htaccess` запрещает прямой доступ к конфигурации, SQL-файлу и служебным материалам; каталог `storage` закрыт отдельным правилом.
